## MODIFIED Requirements

### Requirement: Function call routing via route_to_specialist
The Bridge SHALL handle `response.function_call_arguments.done` events from the OpenAI Realtime API. When the model calls `route_to_specialist()`, the Bridge SHALL emit a `model_router_action` EventEnvelope for **every** valid routing decision, regardless of department. The envelope payload SHALL include `department`, `summary`, and the OpenAI function-call identifiers (`fn_call_id`, `fn_item_id`) needed by the Coordinator to acknowledge the function call and dispatch the follow-up response.

Because the router prompt is sent with `tool_choice="required"`, the model produces only the function call in this response — no audio is generated. Spoken output is produced by separate follow-up responses, all of which are now dispatched by the Coordinator (for both direct and specialist departments).

#### Scenario: Model calls route_to_specialist with direct department
- **WHEN** a `response.function_call_arguments.done` event arrives with `department="direct"`
- **THEN** the Bridge SHALL emit `model_router_action` with `payload={"department": "direct", "summary": "...", "fn_call_id": "<call_id>", "fn_item_id": "<item_id>"}`
- **AND** the Bridge SHALL NOT send `function_call_output` or any follow-up `response.create`

#### Scenario: Model calls route_to_specialist with specialist department
- **WHEN** a `response.function_call_arguments.done` event arrives with `department="billing"`
- **THEN** the Bridge SHALL emit `model_router_action` with `payload={"department": "billing", "summary": "...", "fn_call_id": "<call_id>", "fn_item_id": "<item_id>"}` and clear `_active_voice_generation_id`

#### Scenario: Invalid function call name
- **WHEN** a `response.function_call_arguments.done` event arrives with an unexpected function name
- **THEN** the Bridge SHALL log a warning and not emit any routing event

### Requirement: OpenAI event to EventEnvelope translation (input direction)
The bridge SHALL translate incoming OpenAI Realtime events into Coordinator EventEnvelopes. The following event types SHALL be translated: `input_audio_buffer.speech_started` → `speech_started`, `input_audio_buffer.speech_stopped` → `speech_stopped`, `input_audio_buffer.committed` → `audio_committed`, `conversation.item.input_audio_transcription.completed` → `transcript_final`, `response.function_call_arguments.done` → `model_router_action` (for any valid routing decision, regardless of department), `response.done` → `voice_generation_completed` (only when a spoken response was generated, i.e. not for the initial classification response that produced only a function call), `response.failed` → `voice_generation_error`.

#### Scenario: Committed event translation
- **WHEN** the data channel forwards `input_audio_buffer.committed`
- **THEN** the Bridge SHALL emit an EventEnvelope with `type="audio_committed"` and `source=EventSource.REALTIME`

#### Scenario: Function call with direct triggers routing event
- **WHEN** `response.function_call_arguments.done` arrives with `department="direct"`
- **THEN** the Bridge SHALL emit `model_router_action` with department, summary, and function-call identifiers

#### Scenario: Function call with specialist triggers routing event
- **WHEN** `response.function_call_arguments.done` arrives with `department="billing"`
- **THEN** the Bridge SHALL emit `model_router_action` with department, summary, and function-call identifiers

#### Scenario: Response done after classification (no audio)
- **WHEN** `response.done` fires for a response whose only output was a `route_to_specialist` function call
- **THEN** the Bridge SHALL NOT emit `voice_generation_completed` — the spoken reply is generated by a follow-up dispatched by the Coordinator

#### Scenario: Response done after spoken response
- **WHEN** `response.done` fires for a follow-up `response.create` that produced audio (direct follow-up or specialist say-exactly)
- **THEN** the Bridge SHALL emit `voice_generation_completed` with the accumulated transcript

## REMOVED Requirements

### Requirement: Two-step direct response flow
**Reason**: Direct path orchestration moves to the Coordinator for architectural consistency with the specialist path. The Bridge becomes a pure event translator and no longer sends `function_call_output` ack messages or follow-up `response.create` messages.
**Migration**: The same two-step flow now lives in `Coordinator._on_model_router_action` when `department="direct"`. The Coordinator sends the `function_call_output` ack and a follow-up `response.create` reusing the cached system prompt + history. End-user behavior is unchanged.

### Requirement: Bridge state tracking for pending function calls
**Reason**: With direct-path orchestration moved to the Coordinator, the Bridge no longer needs to track `_pending_fn_call_id` and `_pending_fn_item_id`. The Coordinator receives these identifiers in the `model_router_action` envelope payload and uses them for the function-call acknowledgement.
**Migration**: The Bridge passes `fn_call_id` and `fn_item_id` in the `model_router_action` envelope payload. The Coordinator owns the state from there.

### Requirement: Last instructions caching
**Reason**: With the direct two-step moving to the Coordinator, the Bridge no longer needs to cache `_last_instructions`. The Coordinator already owns the system prompt (built via `RouterPromptBuilder`) and can cache it in `CoordinatorRuntimeState` keyed by `agent_generation_id` for reuse in the direct follow-up.
**Migration**: The Coordinator caches the `instructions` field of each dispatched `response.create` per `agent_generation_id`. The cache entry is cleared on generation completion, cancellation, or error.
